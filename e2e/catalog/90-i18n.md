Five UI locales — `en` (default, unprefixed), `es`, `pt`, `fr`, `de` — from `packages/i18n/messages/{locale}/{common,dashboard,landing}.json`. The hosted app routes by URL prefix (`localePrefix: "as-needed"`); Orkka Local has no prefix and keeps the locale in the `NEXT_LOCALE` cookie. The `LocaleSwitcher` (`<select aria-label="Switch language">`) also persists the member preference (`PUT /api/org/me/preferences {locale}`), which the API prefers over `Accept-Language` when deciding the language agents answer in; a project's own language setting overrides both. Billing currency is decided separately by `X-Orkka-Country` (BR → BRL, else USD).

## I18N-001 Every locale is reachable by URL prefix and English stays unprefixed
```yaml
priority: P0
surface: [ui]
automation: planned
refs:
  - orkka-ui:/p/[projectId]/board
  - orkka-ui:apps/local/i18n/routing.ts
  - i18n:sidebar
since: 2026-09-15
```
**Preconditions**: signed in; Ready project slug S.
**Steps**:
1. Open `/p/S/board`; read the sidebar `Board` label and `<html lang>`.
2. Open `/es/p/S/board`, `/pt/p/S/board`, `/fr/p/S/board`, `/de/p/S/board`; read the same label and `lang`.
3. Open `/en/p/S/board`.
4. Open `/xx/p/S/board`.
**Expected**:
- Unprefixed URL renders English (`lang="en"`, `Board`).
- Prefixed URLs render `lang="es|pt|fr|de"` with the translated `sidebar.board` value from the matching `dashboard.json`.
- `/en/...` redirects to the unprefixed path (as-needed).
- `/xx/...` is treated as a project-less path and results in a 404 page (not a crash).
**Notes**: the API is also called with `Accept-Language: <locale>` derived from the first URL segment (`getClientLocale`).

## I18N-003 Agents answer in the member's language (stored preference over Accept-Language)
```yaml
priority: P1
modes: [hybrid-repo]
surface: [ui, api]
automation: planned
refs:
  - orkka-api:PUT /api/org/me/preferences
  - orkka-api:POST /api/projects/{projectId}/agents/{agentId}/conversations
  - orkka-ui:/p/[projectId]/team
since: 2026-09-15
```
**Preconditions**: Ready project whose `settings.language` is null (Automatic); runner online so chat is $0.
**Steps**:
1. `PUT /api/org/me/preferences {locale:"pt"}`.
2. With `Accept-Language: en-US`, start a conversation with the PM agent and send `Reply with one short sentence about this project.`
3. `PUT ... {locale:"en"}`; send the same message with `Accept-Language: de`.
**Expected**:
- Step 2 reply is in Portuguese (stored preference wins over the header).
- Step 3 reply is in English (stored `en` wins over `de`); with no stored preference at all the header would decide.
**Notes**: language detection can be asserted with a small stopword heuristic (`você/projeto` vs `the/project`). The membership cache is invalidated on each PUT, so no wait is needed.

## I18N-006 Every key exists in all five locale files (parity)
```yaml
priority: P0
surface: [ui]
automation: planned
refs:
  - i18n:meta
  - i18n:sidebar
since: 2026-09-15
```
**Preconditions**: this repository's `ui/` checkout.
**Steps**:
1. Script: for each of `common.json`, `dashboard.json`, `landing.json`, flatten the `en` file and each of `es`, `pt`, `fr`, `de`; compare key sets; compare ICU placeholder sets per key (`{name}`, `{count, plural…}` arguments); check that rich-text tags (`<mono>`, `<b>`, `<code>`, `<link>`) present in `en` are present in the translation.
2. Report missing, extra, and placeholder-mismatched keys per locale.
**Expected**:
- Zero missing keys, zero extra keys, zero placeholder mismatches in all 12 comparisons.
- Namespace counts match the current `en` totals (see `catalog/surface-manifest.json` → `i18n.namespaces`).
**Notes**: implemented as a file check in this repo (no browser); the mobile catalogue has the same test in `orkka-mobile/__tests__/i18n-parity.test.ts`. Line endings differ between locale files — compare parsed JSON, never bytes.

## I18N-009 Dates and relative times follow the active locale
```yaml
priority: P2
surface: [ui]
automation: planned
refs:
  - orkka-ui:/p/[projectId]/tasks/[taskId]
  - orkka-ui:/settings/usage
  - orkka-ui:/p/[projectId]/activity
since: 2026-09-15
```
**Preconditions**: signed in; a task created >1 day ago; usage in the last 30 days.
**Steps**:
1. Open `/p/S/tasks/N` in `en` and `/de/p/S/tasks/N`; read the created/started timestamps in the details grid.
2. Open `/settings/usage` in `en` and `/pt/settings/usage`; read a day label of "Tokens by day" and a token total.
3. Open `/fr/p/S/activity`; read the `24h/7d/30d` window control and any "ago" text.
**Expected**:
- German shows `TT.MM.JJJJ`-style dates and German relative wording (`vor 2 Tagen`); Portuguese shows `DD/MM/AAAA` and `há 2 dias`; English `MM/DD/YYYY` / `2 days ago`.
- Numbers use locale separators (`1.234,56` in de/pt vs `1,234.56` in en) where token counts and estimates are shown.
**Notes**: implemented with `Intl` via next-intl `useFormatter`/`toLocaleString(locale)`; a hard-coded `en-US` format is the regression to catch.

## I18N-011 Glossary `Term` shows a plain-language definition on hover, focus and tap
```yaml
priority: P2
surface: [ui]
automation: planned
refs:
  - orkka-ui:/p/[projectId]/board
  - orkka-ui:packages/ui/src/components/ui/Term.tsx
  - orkka-ui:/settings/preferences
  - i18n:glossary
  - i18n:preferencesPage
since: 2026-09-15
```
**Preconditions**: signed in; `Show technical details` OFF on `/settings/preferences`.
**Steps**:
1. On a page that wraps jargon (e.g. the board or task detail) find `[data-glossary-term]` elements; hover the one with `data-glossary-term="pr"`.
2. Press Tab to focus it; press Escape.
3. Tap it (touch emulation); tap elsewhere.
4. Open `/pt/...` same page and hover again.
5. Turn `Show technical details` ON; reload.
**Expected**:
- Hover opens a card with term `Pull request (PR)` and definition `A proposed set of code changes, packaged so it can be reviewed before it becomes part of the app.`; the trigger has a dotted underline, `tabindex=0`, and `aria-describedby` pointing at the card while open.
- Focus opens, Escape closes; tap toggles, outside tap closes; the card flips below when there is no room above and never clips the viewport.
- In `pt` the term and definition come from `common.json → glossary.pr` of that locale.
- With technical details ON the words render plain (no underline, no card).
**Notes**: glossary keys are validated by `apps/remote/__tests__/i18n/glossary.test.ts`; ICU `'<'` escaping in definitions is a known gotcha.

## I18N-014 API `Accept-Language` normalisation and the `NEXT_LOCALE`/URL precedence in the client
```yaml
priority: P2
surface: [api, ui]
automation: planned
refs:
  - orkka-api:GET /api/org/me
  - orkka-ui:packages/core/src/lib/locale.ts
since: 2026-09-15
```
**Preconditions**: owner API key; signed-in browser session.
**Steps**:
1. `GET /api/org/me` with `Accept-Language: pt-BR,pt;q=0.9,en;q=0.8`, then `PT`, then `xx-YY`, then `de-CH`.
2. In the browser on `/es/inbox` set cookie `NEXT_LOCALE=de` and trigger any API call; inspect its `Accept-Language`.
3. On the unprefixed `/inbox` with the same cookie, inspect again.
**Expected**:
- The API normalises `pt-BR`/`PT` → `pt`, `de-CH` → `de`, and ignores `xx-YY` (unsupported → no locale item; agents fall back to the stored preference or English); the request itself is 200 in every case.
- Step 2 sends `Accept-Language: es` (URL segment wins over cookie); step 3 sends `de` (cookie wins over default when no segment).
**Notes**: `getClientLocale()` order is URL segment → `NEXT_LOCALE` cookie → `en`; the mobile app registers its own getter instead.
