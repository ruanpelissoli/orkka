## Product context (since the 2026-10-26 pivot)
- Orkka is for developers who work several jobs. **One workspace (= one Orkka org) per job**: `GET /api/me/workspaces`, `POST /api/workspaces`, `POST /api/me/active-workspace`; a Clerk-session request names its workspace with `X-Orkka-Workspace: <orgId>` (non-ULID → 400, not a member → 403); API keys stay bound to their own org and ignore the header.
- **One kind of project**: a board plus the developer's repositories. Repos are any git remote added **by URL** (https / ssh / scp-style / ssh host alias; forge detected from the host, overridable with `provider`, plus an optional forge `cliAccount`; credentials in the URL are refused; a folder path is refused) or a **local folder linked through the runner** (`POST /api/projects/{id}/repos/local`).
- **All git and all agent runs happen on the developer's runner** (run in-process by `./orkka start`, one workspace profile per job; `./orkka connect` runs a runner alone) with their own git credentials and their own AI CLI subscription (Claude Code, Codex, Gemini…). No AI CLI signed in ⇒ the task parks `WaitingForRunner` with a note. Cloud execution was removed (orkka-api e3a3a06, 2026-11-17 — no execution target, preference or fallback) and there is no platform-key fallback.
- **Pull requests are Orkka's own review records.** Landing ("merge") = squash-merge into a linked folder, or for a remote **PUBLISH a forge PR** with the runner's `gh` / `az repos` / `glab` (idempotent per head branch; URL on the task as `publishedPrUrl`). Orkka never merges on a forge.
- **Ticket trackers**: `./orkka tracker add jira|ado` stores the token in the OS secret store; the runner reports connection metadata in its Hello (`GET /api/trackers/connections`). A project's **Ticket source** (`GET/PUT/DELETE /api/projects/{id}/tracker`): connection, scope, epics → repo + subfolder, extra JQL/WIQL, include descendants, auto-submit, poll interval 60–300 s, status map (Started / PR opened / Merged), branch template. Settings queries are relayed to the owner's runner (`POST /api/trackers/connections/{id}/query`, offline ⇒ `supported:false`). The runner polls (hub `SyncTrackers` / `ReportTickets`, one poll lease per source): new tickets → tasks `[KEY] title` with `externalKey/externalUrl/externalEpic`; changes rewrite or note; comments → `ExternalComment` messages; tickets that leave are archived or noted. Status write-back via `AckTransitions`: furthest mapped phase only, never backwards, give up after 5 failures (`externalSyncError` on the card).
- **Removed** (no cases): managed/hosted apps (brief, design brief, provisioning, Vercel, Neon, orkka.app, trials, hosted billing), the GitHub App (install, webhooks, issue/CI triggers, create-branch), the installed `orkka-local` binary (release download + signature check, newer-release check, `path add`, `--detach`, the supervisor with Postgres and a Next.js UI server — R4, 2026-11-18), milestone integration branches / ship sweep, billed cloud runs.
- Lanes: Drafting → Ready (PM) → Planning (dev) → PlanReady (human, unless `autoApprovePlan`) → PendingQuestions → Developing → Testing (only if `qaEnabled`/`manualVerificationEnabled`) → CodeReview (human unless `autoApproveCodeReview`) → Done (landed).
- Permissions (18): `TasksCreate, TasksEdit, TasksDelete, TasksExecute, PlansReview, CodeReviewReview, CodeReviewMerge, DocumentsManage, AgentsChat, AgentsConfigure, DesignReview, ProjectsCreate, ProjectsManage, ProjectsDelete, ReposManage, BillingManage, MembersManage, AuditView`. Owners bypass all; reads open to any member; writes 403 without the permission. Ticket-source writes need `ProjectsManage`.

## Test environment assumptions (write preconditions against these)
- **There is no cloud.** The harness targets a sandboxed Orkka on loopback (`E2E_BASE_URL` = `E2E_API_URL` = `http://127.0.0.1:<port>`): `npm run stack:start` runs this clone's build (`dotnet src/Orkka/bin/Release/net10.0/orkka.dll start --no-browser --port <port>`, `ORKKA_HOME=<sandbox>/home`) — one process, host and runner.
- The sandboxed local stack (`npm run stack:start`): its install secret mints the harness API key; every project the harness creates is `e2e-<suite>-<stamp>` (key `E2E`) and is deleted afterwards.
- The runner is the sandboxed Orkka's own (in the same process, `ORKKA_HOME=<sandbox>/home`), with the developer's real AI CLI sign-in; offline CLI cases run `dotnet orkka.dll <verb>` against a throwaway `ORKKA_HOME`.
- **Repos are local bare remotes** behind `https://github.com/e2e-local/<name>.git` aliases (the sandboxed runner's git rewrites them), seeded from `fixtures/repos/orkka-e2e-fixture-web|api`. Forge PRs go through the **stub `gh`** (`fixtures/stub-gh`), which records every call. Standard agent task: add `<token>` to the features list (`app/features.ts` / `src/features.js`).
- **Trackers are the fake Jira Cloud / Azure DevOps server** (`src/fakes/tracker`) on 127.0.0.1; its connection is seeded into the sandbox (`src/runner/tracker-seed.ts`) because `tracker add` cannot target a loopback site.

## Coverage bar
"All features, menus, button clicks, textboxes, configurations." For every page in your areas: one navigation/render case, one case per interactive control (incl. its validation), one per meaningful state (empty, loading, error, permission-hidden, capability-hidden, runner offline), and API-level cases for each endpoint the area owns (happy path + the permission 403 + the notable 4xx).

## Modes and priorities
- `modes`: `hybrid-repo` (remote repo on the runner), `hybrid-folder` (linked folder), `tracker` (a ticket source), `offline` (needs no deployed Orkka: fake servers, stubs, the runner CLI), `all` (shared UI). Use the narrowest true set.
- `priority`: P0 = the core path breaks without it (workspace, project, repo, task to Done/published, ticket → task); P1 = every other primary control; P2 = secondary states/negatives; P3 = cosmetic/rare.
- `automation`: default `planned`. `manual` for a device, a second human account or machine, a real tracker/forge, real payments or emails; `blocked` with `blockedBy` when the product cannot do it yet. Only a case a spec links (`caseIds(...)`) is `automated` (`npm run catalog:sync-automation`).
